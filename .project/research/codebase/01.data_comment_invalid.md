## Research Question
Por que a data do comentário está sendo exibida como inválida no frontend quando retornada via endpoint de tasks, mas não quando retornada via endpoint direto de comments?

## Summary
A análise revelou que o problema está na consulta SQL raw no `task.service.ts` que carrega comentários. A consulta retorna o campo `created_at` dos likes como string no formato PostgreSQL timestamp with time zone, mas quando os dados são serializados pelo interceptor, o formato não é convertido corretamente para Date object JavaScript.

## Detailed Findings

### 1. Consulta SQL Problemática (Task Service)
**File**: `backend/src/modules/tasks/services/task.service.ts`
**Lines**: 75-101

A consulta SQL raw retorna o campo `created_at` dos comment_likes como:
```sql
(SELECT json_agg(json_build_object(
  'id', cl.id,
  'userId', cl.user_id,
  'createdAt', cl.created_at  // ← Este campo é retornado como string PostgreSQL
)) FROM comment_likes cl WHERE cl.comment_id = comment_tree.id) as likes
```

**Problema**: O `cl.created_at` é retornado diretamente do PostgreSQL como string no formato `2025-09-19T18:19:28.780531-03:00`, mas quando serializado pelo interceptor, não é convertido para Date object.

### 2. Entidade CommentLike (Configuração Correta)
**File**: `backend/src/modules/comment/entities/comment-like.entity.ts`
**Lines**: 27-28

```typescript
@CreateDateColumn({ name: 'created_at', type: 'timestamp with time zone' })
createdAt: Date;  // ← Tipo correto: Date
```

### 3. Entidade Comment (Configuração Correta)
**File**: `backend/src/modules/comment/entities/comment.entity.ts`
**Lines**: 39-43

```typescript
@CreateDateColumn({ name: 'created_at', type: 'timestamp with time zone' })
created_at: Date;

@UpdateDateColumn({ name: 'updated_at', type: 'timestamp with time zone' })
updated_at: Date;
```

### 4. Transform Interceptor
**File**: `backend/src/common/interceptors/transform.interceptor.ts`
**Lines**: 24-31

O interceptor apenas encapsula a resposta, mas não faz transformação de tipos de dados. A serialização é feita automaticamente pelo Nest.js/Express.

### 5. Comparação: Endpoint Comments vs Tasks

#### Endpoint `/comments` (Funciona):
- Usa TypeORM com relações
- Retorna objetos Date corretamente serializados
- Exemplo: `"created_at": "2025-09-19T21:19:25.103Z"`

#### Endpoint `/tasks/:id` (Problema):
- Usa SQL raw
- Retorna strings PostgreSQL diretamente
- Exemplo: `"createdAt": "2025-09-19T18:19:28.780531-03:00"`

## Architecture Insights

1. **Dual Approach**: O sistema usa tanto TypeORM (para maioria das operações) quanto SQL raw (para consultas complexas)
2. **Serialização Automática**: Nest.js serializa automaticamente objetos Date para ISO strings
3. **Timezone Configuration**: PostgreSQL está configurado com timezone, mas a consulta raw não aproveita a conversão automática do TypeORM

## Historical Context

O uso de SQL raw foi provavelmente implementado para otimizar a carga de comentários aninhados, mas introduziu esta inconsistência na serialização de datas.

## Recommended Solution

Modificar a consulta SQL para converter explicitamente o timestamp para formato ISO:

```sql
'createdAt', cl.created_at::timestamp with time zone AT TIME ZONE 'UTC'  // Converter para UTC
```

Ou alternativamente, processar as datas manualmente após a consulta:

```typescript
// Após a consulta, converter strings para Date objects
comments.forEach(comment => {
  if (comment.likes) {
    comment.likes = comment.likes.map(like => ({
      ...like,
      createdAt: new Date(like.createdAt)
    }));
  }
});
```

A primeira abordagem (no SQL) é mais eficiente e consistente.
